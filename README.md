## О проекте

**Календарь звонков** — упрощённый аналог Cal.com для планирования и бронирования встреч.

Владелец создаёт типы встреч с описанием и длительностью, а гости самостоятельно выбирают подходящее время и бронируют встречи. Для обеих ролей регистрация не требуется: функции владельца доступны по заранее определённому URL.

Сервис показывает только время, которое соответствует расписанию владельца и не занято другими встречами.


Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers  
Как это должно работать: https://files.hexlet.app/a/2ipc5m


## Публичное приложение

https://calendar-calls-sdg9.onrender.com

Приложение задеплоено на Render из ветки `main` как Docker web service. Пуш в `main` запускает автодеплой.

## Локальная разработка

Для работы нужен [mise](https://mise.jdx.dev/). Он устанавливает зафиксированные в проекте версии Node.js `24.22.3` и pnpm `12.17.0`. Обязательные переменные окружения не требуются.

Workspace содержит два приложения: React + Vite frontend в `apps/frontend` и Node.js + Express backend в `apps/backend`.

### Установка

```sh
mise install
pnpm install
pnpm --filter frontend exec playwright install chromium
```

Зависимости обоих приложений устанавливаются из корня pnpm workspace и фиксируются в одном общем `pnpm-lock.yaml`.

### Запуск

```sh
pnpm dev
```

Команда средствами pnpm параллельно запускает frontend и backend. Отдельный пакет-оркестратор не используется.

- Главная страница frontend доступна по адресу `http://localhost:5173/`, страница владельца — `http://localhost:5173/admin`.
- Backend слушает порт `3000`. Прямая проверка: `http://localhost:3000/api/health`.
- Vite проксирует запросы с префиксом `/api` на `http://localhost:3000`. Frontend вызывает API по относительному адресу `/api` без CORS и без переменных окружения.

Перед запуском backend автоматически применяет Drizzle-миграции. Типы встреч хранятся в PGLite в `apps/backend/data`; необязательная переменная `DATA_DIR` позволяет выбрать другой каталог.

### Контракт и миграции

Предметные операции описаны в `apps/backend/api/main.tsp`. После изменения контракта выполните `pnpm --filter backend api:generate && pnpm --filter frontend api:generate`. Production-сборка повторяет генерацию автоматически. После изменения схемы БД новая миграция создаётся командой `pnpm --filter backend drizzle:generate`.

### Docker

```sh
docker build -t calendar-calls .
docker run --rm -p 3000:3000 -v calendar-calls-data:/app/data calendar-calls
```

Контейнер стартует автоматически. Порт берётся из `PORT`, по умолчанию `3000`. Страница и `/api/health` доступны на одном порту.

### Проверки

Из корня проекта выполняются проверки обоих приложений:

```sh
pnpm lint
pnpm test
pnpm build
mise run check
```

`pnpm lint`, `pnpm test` и `pnpm build` охватывают frontend и backend. `pnpm test` запускает Vitest и Playwright: браузерный сценарий сам поднимает изолированные frontend/backend с временной БД. `pnpm build` компилирует OpenAPI и клиентские типы, проверяет TypeScript и создаёт production-сборки в `apps/frontend/dist` и `apps/backend/dist`. `mise run check` проверяет существующие GitHub Actions workflows.


## Роли

### Владелец

Владелец управляет календарём и может:

- просматривать список типов встреч;
- создавать типы встреч с описанием и длительностью;
- просматривать встречи, забронированные гостями, включая их тип, дату и время, а также имя и почту гостя.

### Гость

Гость может без регистрации:

- просматривать доступные типы встреч;
- выбирать тип встречи;
- просматривать свободные слоты;
- бронировать встречу, указывая своё имя и почту.

## Правила доступности

- Владелец принимает встречи по будням, с понедельника по пятницу, с 09:00 до 18:00.
- Расписание владельца задано в часовом поясе `Europe/Moscow` (UTC+03:00, без перехода на летнее время).
- Выходные дни недоступны для бронирования.
- Гость видит свободные слоты на ближайшие 14 дней от текущего момента.
- Слоты отображаются в часовом поясе гостя.
- Возможное время начала встречи предлагается с шагом 15 минут: 09:00, 09:15, 09:30 и так далее по времени владельца.
- Встреча должна полностью укладываться в рабочие часы владельца.
- Время, занятое забронированной встречей, недоступно для других встреч. Новая встреча не может пересекаться с уже существующей.


## Основные сценарии

### Создание типа встречи

1. Владелец открывает список типов встреч.
2. Если нужного типа нет, владелец создаёт его, указывая описание и длительность.
3. Созданный тип становится доступен гостям для бронирования.

### Бронирование встречи

1. Гость открывает список типов встреч и выбирает нужный.
2. Сервис показывает свободные слоты на ближайшие 14 дней с учётом расписания владельца, длительности выбранной встречи и существующих бронирований.
3. Гость выбирает подходящий слот.
4. Гость указывает имя и почту и подтверждает бронирование.
5. Встреча появляется в списке встреч владельца, а занятое время исключается из доступности для других гостей.

### Просмотр забронированных встреч

Владелец открывает список встреч и просматривает их параметры и данные гостей.

В текущей версии поддерживаются только создание и просмотр встреч. Отмена и перенос бронирований не предусмотрены.
